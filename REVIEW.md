# REVIEW.md

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `attendance_date` / `late_minutes` / `overtime_minutes` | Time logic used naive assumptions and the wrong shift-date anchor for overnight shifts. | A 22:00-06:00 shift crossing midnight and late punch-ins around 03:00 produced incorrect attendance dates and lateness. | Normalized to UTC, converted to IST for comparison, and anchored attendance-date logic to the shift start on the correct attendance day. |
| 2 | `work_hours` / `half_day` | Rounding used the wrong approach and could produce 4.67 instead of 4.68 for a 4h 40m 30s span. | Calculations near 4.5 hours and Decimal rounding tests showed values under the contract. | Switched to Decimal half-up rounding and kept `half_day` tied to the rounded work hours. |
| 3 | `EmployeeIn` / `PunchInIn` / `RegularizeIn` | Models accepted invalid timestamps, extra data, and values that violate the contract. | Strict validation tests on strings, floats, nulls, and out-of-range epoch milliseconds failed. | Added bounded strict integer validation and explicit field restrictions to reject invalid payloads with 422. |
| 4 | `create_employee` and attendance creation | Duplicate handling relied on application-level checks rather than database guarantees. | Concurrent inserts could create duplicate employees or duplicate attendance rows. | Added unique MongoDB indexes and caught `DuplicateKeyError` to return 409 responses. |
| 5 | `punch_out` | The code chose a punch-in without enforcing the same-day/correct-window constraints and could allow invalid intervals. | Punch-out before punch-in or over 24 hours failed to be rejected cleanly. | Enforced `punch_in <= punched_at <= punch_in + 24h` with a single atomic winner selection. |
| 6 | `regularize_attendance` | PATCH logic allowed inconsistent state changes and did not protect against concurrent modifications. | Repeated regularizations or race conditions could overwrite newer changes. | Implemented compare-and-update with prior snapshot matching before applying `$set` and `$push` to history. |
| 7 | `serialize_employee` / `serialize_attendance` | The starter returned raw Mongo documents with `_id` leakage and unconverted times. | API responses included internal IDs or wrong time formats. | Added explicit serializers that strip `_id`, convert instants to epoch milliseconds, and clamp legacy values. |
| 8 | Monthly analytics | The starter did not compute department or monthly summaries correctly and did not use stored values consistently. | Department totals and employee monthly results undercounted or used recomputed values instead of stored data. | Aggregated against MongoDB while reading stored `work_hours`, `late_minutes`, and `half_day` values directly. |
| 9 | Department/timeline analytics | No gap-filling or trend pipeline existed; weekends and zero-record dates were ignored. | Daily trends omitted blank dates, weekends, and headcount-scope days. | Added date-range generation and `$densify`/window calculations to return one row per requested calendar day. |
| 10 | Leaderboard logic | No ranking pipeline existed, and ties were not handled using competition ranking. | Missing route and incorrect ordering could not satisfy contract requirements. | Added ranking with `$setWindowFields` and filtered by `rank <= limit` after ranking. |
| 11 | Admin explain | No execution-plan endpoint existed. | The contract required a raw MongoDB `explain` response for named endpoints. | Added `/admin/explain/{endpoint}` that builds the same aggregation/query shape and returns `executionStats`. |

Not a defect: the project intentionally keeps MongoDB IDs out of API payloads and computes month-level values in the database, because the contract explicitly requires aggregation to happen at the database layer and forbids exposing internal document IDs. These choices are deliberate contract requirements and were not defects to be removed.
